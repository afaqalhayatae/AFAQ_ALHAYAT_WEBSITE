## 3. SEO Filename Rules

Per `99_STANDARDS/NAMING_CONVENTIONS.md`'s approved `<service-or-purpose>-<context>-v<N>.<ext>` pattern, applied strictly:

- **Lowercase only** — no mixed case, ever (`pest-control-hero-v1.webp`, never `Pest-Control-Hero-V1.webp`).
- **Descriptive, not generic** — the filename must say what the image shows (`pest-control-inspection-detail-v1.webp`), never `img1.webp` or `photo-final.webp`.
- **Keyword-focused, not keyword-stuffed** — one clear service/purpose phrase per filename, not a string of every possible keyword joined with hyphens.
- **No random names** — no auto-generated camera filenames (`IMG_4821.jpg`), no timestamps as the primary identifier.
- **Web-friendly format** — hyphens only (no spaces, underscores, or special characters), ASCII characters only (Arabic-language images still get an ASCII filename; the Arabic fact lives in the alt text, per §4).

**Example (as given):** `pest-control-dubai-service.webp` — matches the pattern; this library's own filenames (e.g., `pest-control-homepage-hero-v1.webp`) additionally include the version suffix per the naming standard's explicit examples.

## 4. Alt Text Rules

Per `12_DESIGN_SYSTEM/ACCESSIBILITY.md` and `11_VISUAL_ASSET_STRATEGY.md` §6:

### Arabic SEO requirements
- Natural Arabic phrasing describing what the image shows — never a mechanical translation of the English alt text, per `PROJECT_MANIFEST.md`'s bilingual-equality principle.
- No diacritics required; standard modern-standard-Arabic phrasing consistent with the rest of the site's Arabic content.

### English SEO requirements
- Specific and descriptive ("Technician inspecting a Dubai property for pest activity," not "pest control service").
- Includes the real subject and context, not just the service name repeated.

### Natural language, no keyword stuffing (both languages)
- Alt text describes the image; it is not a second place to cram every target keyword. If a keyword doesn't naturally describe what's in the photo, it doesn't belong in that photo's alt text.
- Alt text may never assert a fact the image doesn't support, and may never contain an unapproved claim (certification, safety guarantee, speed promise) even if that claim exists elsewhere in draft copy — same evidence gate as visible text, per `VISUAL_ASSET_BRIEF.md` §0.
- Decorative/illustrative placeholder art (the current `BrandPanel` line-art) stays `aria-hidden` with no alt text, unchanged by this library.

## 5. AI Image Generation Rules

Extends `11_VISUAL_ASSET_STRATEGY.md` §3 and `VISUAL_ASSET_BRIEF.md` §6 with the six explicit rules requested — all six are already consistent with, not additions beyond, this repository's existing Hard Publication Blocks:

1. **Luxury UAE service brand style** — calm, confident, restrained composition per `LUXURY_DESIGN_DIRECTION.md` §2/§3; no "cheap gold-on-black luxury clichés" (§10 of that document).
2. **Clean, professional look** — organized equipment, tidy uniforms, controlled lighting; no clutter or staged drama.
3. **No fake certifications** — no badge, seal, or credential graphic invented or implied in a generated image, per this package's Evidence Gate.
4. **No fake customer identities** — no AI-generated "customer" presented as if a real, named person exists; any customer-facing image requires real, documented consent (§4/`BRAND_IMAGES.md`).
5. **No misleading results** — no AI-generated "after" or before/after pairing; before/after imagery requires real, verified evidence per `11_VISUAL_ASSET_STRATEGY.md` §2, which does not exist yet.
6. **Consistent visual identity** — same illustration style, color grading, and stroke/composition language as the existing `brand-scenes.tsx` illustrations across every generated placeholder, so nothing looks like it came from a different brand.

**Absolute constraint carried over unchanged:** any AI-generated asset remains illustration-style only, never photorealistic, per `LUXURY_DESIGN_DIRECTION.md` §10's prohibition on "AI-generated media presented as real company evidence." ## 6. Performance Rules

Per `05_SEO_IMPLEMENTATION_PLAN.md` §1 and `LUXURY_DESIGN_DIRECTION.md` §9 (already-approved standards, restated here as this library's own checklist, not redefined):

- **Format:** WebP preferred (per `BRAND_IMAGES.md`/`NAMING_CONVENTIONS.md`); AVIF may be used where the delivery pipeline supports it, with WebP as fallback — format negotiation is handled by the app's existing `next/image` usage, not a new pipeline this document invents.
- **Compression:** every image optimized before upload; no unoptimized camera-original file ships to production.
- **Responsive sizes:** images serve appropriately sized variants per viewport (already the default behavior of the app's `next/image` usage in `BrandPanel` with its `sizes` prop) — no fixed oversized image forced onto mobile.
- **Lazy loading:** below-the-fold images load lazily by default; only the true hero/LCP image is eagerly loaded (`priority`), matching the existing pattern already used for the header logo.
- **Core Web Vitals:** no image may be the cause of a layout shift — dimensions are always known/reserved ahead of load; hero images are weighed against LCP budget before being finalized at full resolution.

## 6b. Correction Pass (2026-07-28) — Format Fixed, Content Fixes Blocked

A controlled correction pass was requested against `pest-control-homepage-hero-v1.webp` and `cockroach-control-service-card-v2.webp`. Result: **format issue resolved and verified; content issues could not be safely resolved with the tools available in this environment, and were not attempted rather than faked.**

**A) File format — DONE, verified.** Both files were re-encoded in place, filenames unchanged, using a lossless WebP re-encode (Pillow/`libwebp`, `lossless=True`), preserving every pixel exactly:
- Binary signature confirmed via `xxd`: both now start `52 49 46 46 ... 57 45 42 50 56 50 38 4C` (`RIFF....WEBPVP8L`) — a true WebP container, not a renamed PNG.
- Pixel-for-pixel identity confirmed against the pre-conversion file (`PIL.ImageChops.difference` → empty bounding box) — the re-encode changed the container format only, not a single pixel of content, so this step could not have altered branding, layout, colors, or text.

**B) Hero content corrections ("CLEANLIIESS" → "CLEANLINESS", garbled secondary wordmark cleanup) — NOT IMPLEMENTED.** Blocked, not skipped: the typo sits on a photographic, perspective-skewed van door with its own lighting and shadow. No photo-retouching/inpainting tool is available in this environment (no Photoshop-equivalent, no AI inpainting API configured), and the task explicitly disallows generating a new image to fix it. A programmatic rectangle-and-text patch was considered and rejected: without perspective correction, font matching, and lighting simulation, it would sit on the photo as a visibly flat, mismatched patch — a worse outcome than the current typo, and arguably itself a "design style" change the task prohibits. This needs a real photo editor or a targeted inpaint by whoever can access the original generation tool.

**C) Service card content corrections (remove guarantee/absolute-safety/eco-product claims, verify Arabic spelling) — NOT IMPLEMENTED, Arabic spelling independently verified.** Same blocker as (B) for the pixel edits: rewriting badge text convincingly requires either inpainting or a text-and-shape overlay. For English text this is at least mechanically renderable, but the badges needing removal here are Arabic ("نتائج مضمونة", the family/pets claim, the eco-friendly claim), and this environment's Pillow install does not have `libraqm` (`PIL.features.check('raqm')` → `False`) — the library required for correct Arabic letter joining/shaping. Drawing Arabic text without it produces disconnected, incorrectly-shaped glyphs, i.e., programmatically "fixing" this image would risk introducing a *new* Arabic-rendering defect of the same kind already flagged, on a document that exists specifically to catch that class of error. This was not attempted. ## 6e. Footer Spelling Fix — Resolved (2026-07-28)
